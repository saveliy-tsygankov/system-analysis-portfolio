# 8. Диаграмма последовательности и API

## 8.1 Диаграмма последовательности UC-4

Диаграмма раскрывает шаги 9–12 сценария UC-4 по времени и показывает две ветки отказа: некорректные данные (4.E1) и занятое время (4.E2). Участники: клиент, браузер, сервер сайта, база данных, сервис уведомлений. Исходник: [diagrams/sequence-uc4.mmd](../diagrams/sequence-uc4.mmd).

![Диаграмма последовательности UC-4](../diagrams/sequence-uc4.png)

| Шаг сценария | Сообщения |
| --- | --- |
| Шаг 9: клиент нажимает «Записаться» | 1–2 |
| Шаг 10: проверка формата и полноты | заметка после 2, ветка 3–4 (4.E1) |
| Шаг 10: проверка времени | внутри сообщения 5 |
| 4.E2: время занято | 6–10 |
| Шаг 11: создание записи и закрепление времени | 5, 11 |
| Шаг 12: подтверждение и передача уведомления | 12–15 |

Ключевые решения:

- Проверка времени и закрепление слота идут одним сообщением к базе данных (одна транзакция): так выполняются FR-7 и тест конкурентной записи из НФ-12.
- Формат данных проверяет сервер до обращения к базе (FR-9), поэтому некорректный запрос не нагружает базу.
- Клиент получает подтверждение до передачи уведомления: сторонний сервис не замедляет ответ (НФ-2), а недоставленное уведомление обрабатывается по 4.E4.
- Ветки 4.E3 (сбой сохранения) и 4.E4 (недоставленное уведомление) вынесены из схемы, чтобы она оставалась читаемой.

## 8.2 Методы API

Контракт: [api/openapi.yaml](../api/openapi.yaml) (открывается в Swagger Editor). Коллекция запросов: [api/postman](../api/postman/booking.postman_collection.json). Методы клиентской части открыты без входа (гостевая запись); методы админ-панели в контракт не входят.

| Метод | Назначение | Шаг сценария |
| --- | --- | --- |
| GET /services | Каталог услуг | UC-4, шаг 1; ВИ-1 |
| GET /photographers | Фотографы и портфолио | UC-4, шаг 3; ВИ-2 |
| GET /photographers/{id}/slots | Свободное время | UC-4, шаг 5 |
| POST /bookings | Создание записи | UC-4, шаги 9–12 |
| POST /bookings/{id}/cancel | Отмена записи | ВИ-7 |

Общие правила:

- Формат данных JSON, даты в ISO 8601 с часовым поясом, поля в snake_case, цена строкой с двумя знаками.
- Идентификатор записи, статус, канал, время окончания и время создания задаёт сервер, клиент их не присылает.
- Единый формат ошибки: объект `error` с полями `code`, `message` и, для 400, массив `details` из пар `field` и `message`; для 500 добавляется `request_id`.
- Коды 4xx означают ошибку клиента, 5xx сбой сервера; при 500 технические подробности не раскрываются.
- Порядок проверок: формат (400), существование (404), допустимость сочетания (409).
- `POST /bookings` защищён от двойного нажатия заголовком `Idempotency-Key`: повторный запрос возвращает прежний ответ и не создаёт вторую запись.
- Отмена доступна по секретному токену из уведомления; в базе хранится только его хэш.

Коды ошибок по методам:

| Код | Код ошибки | Где возникает |
| --- | --- | --- |
| 400 | VALIDATION_ERROR | все методы с параметрами и телом |
| 404 | SERVICE_NOT_FOUND | GET /photographers, GET slots |
| 404 | PHOTOGRAPHER_NOT_FOUND | GET slots |
| 404 | BOOKING_NOT_FOUND | POST cancel |
| 409 | SERVICE_NOT_PROVIDED | GET slots, POST /bookings |
| 409 | SLOT_UNAVAILABLE | POST /bookings (в теле свободные слоты) |
| 409 | CANCEL_TOO_LATE, CANCEL_NOT_ALLOWED | POST cancel |
| 500 | INTERNAL_ERROR | все методы |
