# База данных

PostgreSQL 14 и выше. Схема построена по разделу 9 документа «Модель данных».

## Запуск

Создайте пустую базу и выполните файлы по порядку.

Через psql:

```
psql -U postgres -c "CREATE DATABASE photo_studio"
psql -U postgres -d photo_studio -f 01_schema.sql
psql -U postgres -d photo_studio -f 02_seed.sql
psql -U postgres -d photo_studio -f 03_queries.sql
psql -U postgres -d photo_studio -f 04_double_booking_test.sql
```

Через DBeaver: подключиться к PostgreSQL, создать базу `photo_studio`, открыть каждый файл и выполнить как скрипт (Alt+X).

PostgreSQL можно поднять в Docker:

```
docker run --name studio-db -e POSTGRES_PASSWORD=postgres -p 5432:5432 -d postgres:16
```

## Файлы

| Файл | Содержание |
| --- | --- |
| `01_schema.sql` | Таблицы, ключи, ограничения, перечисления, индексы |
| `02_seed.sql` | Вымышленные данные: 3 услуги, 2 фотографа, график на 2 месяца, 8 записей |
| `03_queries.sql` | 11 запросов: свободные слоты, отчёт владельца, эскалации, обезличивание |
| `04_double_booking_test.sql` | Проверка того, что один слот нельзя занять дважды |

## Ключевые решения

- **Свободные слоты не хранятся**, а вычисляются запросом Q1: рабочие интервалы минус активные записи (FR-12–FR-14).
- **Один слот не займут дважды.** Ограничение `bookings_no_overlap` (EXCLUDE USING gist) запрещает пересекающиеся записи одного фотографа, кроме отменённых. Так база обеспечивает FR-7 при одновременных запросах.
- **Клиента не удаляют, а обезличивают** (`anonymized_at`): записи остаются, и отчёты по БЦ-1 и БЦ-2 не меняются (НФ-11).
- **Токен отмены хранится хэшем** (`cancel_token_hash`), пароли сотрудников тоже (НФ-9).
- **Формат данных проверяется и в базе** (CHECK на имя, телефон и email из FR-2–FR-4), но главная проверка выполняется на сервере (FR-9).
